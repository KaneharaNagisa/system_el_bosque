２、予約フォーム（宿泊日程の選択）

- 予約可否の判定は必ず管理画面＞マスタ管理＞予約枠管理（`availabilities`テーブル）のデータを正としてください。
- 日付ごとの判定ルール（優先順）
  1.  `availabilities`テーブルに明示的な登録がある場合は、その`status`に従う（`available`=空きあり、`booked`=予約済み、`cleaning`=清掃準備中、`closed`=予約不可、`manual_blocked`=予約不可、`offseason`=休業期間）。
  2.  登録が無い日付は、営業期間（毎年3月〜12月）内かつ本日以降であれば「空きあり」とみなす。
  3.  登録が無い日付でも、火・水・木は定休日として「予約不可」とみなす。
  4.  営業期間外、または本日より前の日付は「休業期間」として選択不可にする。
- 上記の判定は、日程選択欄（チェックイン・チェックアウトの入力カレンダー）と、その下に表示される空き状況カレンダーの両方で一致させること。管理画面で「予約不可」に設定した日付は、どちらのカレンダーからも選択できないようにする。

### 予約フォーム・予約確定画面の保留中予約制御

- 予約確定処理では、`availabilities`テーブルに明示的な登録が無い日付も、上記の日付ごとの判定ルールに従って予約可否を判定する。エンドユーザー側のカレンダーでは空きありに見えるのに、予約確定時だけ予約不可になる状態を作らないこと。
- 予約確定処理で新規予約を作成する場合、予約ステータスは`pending`（保留中）で登録する。
- 同一ユーザーが、同一チェックイン日・同一チェックアウト日の`pending`（保留中）予約を再度確定する場合は、新規作成せず既存の`pending`予約を利用して予約完了画面へ遷移させる。
- 別ユーザーの`pending`または`confirmed`予約、または同一ユーザーでも日程が異なる予約と重複する場合は、予約不可として扱う。

３、マイページの予約履歴

- ログイン済みの会員がマイページを表示した場合、自分自身の予約履歴だけを表示する。
- 予約履歴はチェックイン日の新しい順に表示する。
- マイページ上の予約履歴は、直近3件だけを表示する。
- 予約履歴が3件以下の場合は、マイページに表示されている予約履歴だけで完結し、別の予約履歴画面への導線は表示しない。
- 予約履歴が4件以上ある場合は、マイページに直近3件を表示し、残りの予約を含む全件を確認できる予約履歴画面への導線を表示する。
- 予約履歴画面では、ログイン中の会員自身の予約履歴を全件表示する。
- マイページと予約履歴画面では、予約ごとの予約番号、チェックイン日、チェックアウト日、人数、ペット、滞在サポート、支払い合計、予約ステータスを確認できるようにする。

## エンドユーザー側画面の追加仕様

### 1. 画面構成

- 画面はエンドユーザー向けの公開ページとして、以下を基本とする。
  - トップページ
  - 予約フォーム（宿泊日程の選択）
  - 予約確定画面
  - ログイン画面
  - マイページ
  - 予約履歴画面
  - 施設紹介
  - 周辺情報
  - よくある質問
  - お問い合わせ
  - 利用規約
  - 個人情報取り扱い
- 画面遷移は管理画面で公開設定された固定ページやメニューに従い、管理画面側の情報を利用して表示する。
- 各画面は、PC・タブレット・スマートフォンで表示崩れが起きないようにレスポンシブ対応を行う。
- 管理画面側のソースコードや画面構成は変更せず、公開側のみの実装として対応する。

### 2. トップページ

- トップページは http://localhost:8000/ で表示され、エンドユーザー側の最初の入口とする。
- ヘッダーには、施設紹介、周辺情報、予約、マイページ、ログイン状態に応じた会員メニューなどを配置する。
- 上部にはメインビジュアル、簡単な施設紹介、予約への導線、公開中のお知らせを表示する。
- 下部には、宿泊の魅力、周辺景観、アクセス情報、予約フローなどの紹介を配置する。
- お知らせは管理画面で設定した公開期間内のもののみ表示し、未公開の情報は非表示とする。
- 予約CTAは「空き状況を確認する」または「宿泊日程を選ぶ」などの明確な導線にする。

### 3. 施設紹介・周辺情報

- 施設紹介ページでは、宿泊施設の特徴、設備、利用方法、周辺の雰囲気を説明する。
- 周辺情報ページでは、周辺の観光スポット、景観、立地情報、徒歩・車でのアクセスなどを案内する。
- 画像は管理画面の画像管理で差し替え可能な公開画像を利用する。
- 画像未設定時は既存の静的画像を表示し、レイアウトが崩れないようにする。
- 周辺情報画面の「秋の風景」の上の湖画像は、選択項目として必ず利用可能にする。

### 4. 会員ログイン・マイページ

- http://localhost:8000/login は会員用のログイン画面とし、会員アカウントでログインする形式を基本とする。
- ログイン後、会員専用のマイページへ遷移する。
- マイページでは、会員情報の表示と編集機能、予約の確認、ログイン状態の維持を行う。
- マイページに表示する予約履歴は、自身の予約のみを対象とする。
- ログインしていない場合は、会員用ページへアクセスしてもログイン画面へ誘導する。

### 5. 予約フォーム

- 予約フォームは宿泊日程の選択から開始し、チェックイン日・チェックアウト日を選択する入力欄を提供する。
- 予約可否判定は管理画面の予約枠管理（`availabilities`テーブル）を正とし、以下のルールに従う。
  1. `availabilities`テーブルに明示的な登録がある場合は、その`status`を優先する。
  2. 登録がない日付は営業期間（毎年3月〜12月）内かつ本日以降なら空きありとみなす。
  3. 登録がない日付でも火・水・木は定休日として予約不可とする。
  4. 営業期間外または本日より前の日付は休業期間として選択不可とする。
- 日程選択カレンダーと空き状況カレンダーは同じ判定ロジックを使用し、管理画面で予約不可に設定した日付は両方から選択できないようにする。
- 予約画面では、予約可能な日付だけが選択可能で、不可日付は視覚的に明確に区別する。
- 予約確定時にも同じ判定ルールを再確認し、エンドユーザー側で見えている空き状態と予約確定時の判定が不一致にならないようにする。

### 6. 予約確定・保留中予約制御

- 新規予約を確定する際、予約ステータスは `pending`（保留中）で登録する。
- 同一ユーザーが、同一チェックイン日・同一チェックアウト日の `pending` 予約を再度確定しようとした場合は、新規作成せず既存の `pending` 予約を利用して予約完了画面へ遷移する。
- 別ユーザーの `pending` または `confirmed` 予約、または同一ユーザーで日程が異なる予約と重複する場合は、予約不可とみなす。
- 予約完了画面では、予約番号、滞在日程、人数、ペット、滞在サポート、支払い合計、予約ステータスを表示する。
- 予約完了画面は、保留中予約の再利用時でも既存予約の情報を正しく表示する。

### 7. マイページと予約履歴

- マイページでは、ログイン中の会員に紐づく予約履歴のみを表示する。
- 予約履歴はチェックイン日の新しい順に並べる。
- マイページ上では直近3件までを表示し、4件以上ある場合は残りの予約を確認できる導線を表示する。
- 予約履歴が3件以下の場合は、別画面への導線を表示しない。
- 予約履歴画面では、会員自身の全予約を一覧表示する。
- 各予約には、予約番号、チェックイン日、チェックアウト日、人数、ペット、滞在サポート、支払い合計、予約ステータスを表示する。

### 8. お問い合わせ・FAQ・利用規約

- お問い合わせフォームは公開画面から入力できるようにし、管理画面のお問い合わせ管理に一覧表示されるようにする。
- よくある質問は管理画面で設定した内容を表示する。
- 利用規約、個人情報取り扱いなどの固定ページは管理画面の固定ページ管理で更新可能なものを表示する。
- エンドユーザー画面で表示するテキストや公開情報は、管理画面側のデータソースを優先して表示する。

### 9. 公開側の運用ルール

- 公開画面に表示する画像、テキスト、ニュース、お知らせなどは、管理画面の登録内容を優先して表示する。
- 管理画面のデータが未設定の場合は、既存の静的コンテンツを表示して画面が崩れないようにする。
- 仕様にない追加機能や独自の画面を勝手に増やさず、既存の要件に沿って実装する。
- すべての公開画面は、管理画面側の予約枠情報・会員情報・公開設定を参照して動作させる。
